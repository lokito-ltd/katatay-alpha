## Why

The release tarball was built by hand on a laptop and uploaded to a GitHub
Release by hand. Nobody could check where a downloaded `katatay-0.1.0.tgz` came
from, and no merged change had a build anyone could try.

The version was typed into `packaging/katatay/package.json` and copied by hand
into the README. Bumping it took a pull request, and every pull request here
pays the full referee workflow. The operator chose to take the version from git
tags, so a release is one pushed tag and no pull request.

## What

- `.github/workflows/build.yml` builds the tarball for every pull request,
  every push to `main` and every `v*` tag, and keeps it as a workflow artifact.
- Pushes and tags sign the tarball with a GitHub artifact attestation, keyless
  through Sigstore. Pull requests are not signed: a fork's pull request gets no
  signing identity, and only merged code should carry a signature.
- A `v*` tag must be on `main` and name the tarball's version. The workflow
  then publishes a GitHub Release with the tarball attached as
  `katatay-<version>.tgz` and as `katatay.tgz`. A tag with a pre-release, such
  as `v0.3.0-rc.1`, makes a GitHub pre-release.
- The version comes from `git describe --tags --match 'v*' --long --dirty`:
  `0.2.0` on a clean release tag, `0.2.0+3.gabc1234` three commits later, with
  `.dirty` added for uncommitted edits, also on the tag itself.
- `npm run pack:katatay` stamps that version into the packed `package.json`,
  and `ktty version` in a source checkout prints it. An installed `ktty` still
  reads its own `package.json`.
- With no `v*` tag in reach, packing fails and the source `ktty version` exits
  1. Both name `git fetch --tags`. Neither makes up a version.
- `packaging/katatay/package.json` keeps `0.0.0` as a placeholder nobody edits.
- The README installs from the latest release's `katatay.tgz` and shows how to
  check a download with `gh attestation verify`. `CLAUDE.md` gains "Releasing
  here".

Out of scope: reproducible builds across machines, parked in the follow-ups
file; publishing to the npm registry; a rolling development pre-release; and
`verify.yml`.

## How

**The version names the source; the attestation names the file.** The tarball
is not promised to be byte-for-byte the same across machines, so the version
says which commit was built and the attestation binds the exact file by its
hash. Both copies on a release have the same bytes, so one attestation covers
both.

**Tags, not a version in a file.** Bumping a version ahead of the release, or
at release time, needs a pull request per release. A run id or run number was
rejected: a re-run keeps the same run id, and neither says which code was
built. release-please and changesets were rejected because a bot's branch has
no referee logbook, so `state-verify` and the guard would refuse its pull
request.

**Build metadata after `+`.** SemVer ignores it for ordering, so `0.2.0+3.g…`
sorts with `0.2.0` and never looks newer than a later release. The `g` before
the short commit keeps a hash such as `0123abc` from being read as an invalid
number part.

**A workflow of its own.** `verify.yml` cancels an older run when a newer push
arrives. Two merges close together on `main` would then lose the first one's
signed build. In `build.yml` only pull request runs cancel each other; each
push to `main` or tag runs in its own group.

**Keyless signing over a stored key.** A GPG key in a repository secret can
leak, needs rotating, and its public key has to be published somewhere. The
attestation uses the workflow's own short-lived identity, and the signing
permissions are granted to the build job alone.
